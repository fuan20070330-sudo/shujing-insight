# 数镜 · 3 分钟演示脚本

> 目标：在 180 秒内讲清“为什么需要数镜、它做了什么、如何证明结论可信、技术如何实现”。
> 建议提前打开线上或本地生产预览，窗口宽度 1440px，浏览器缩放 100%。

## 0:00–0:18 开场命题

**操作**：停留在首页首屏。

**讲解词**：

“评委老师好，我们的作品是数镜。自动数据分析最大的问题不是生成结论不够快，而是结论常常无法验证。数镜想解决的是：让每一个结论，都有一条回到原始数据和统计证据的路。”

**画面重点**：

- 标题“让每一个结论，都有一条回家的路”；
- 浏览器本地计算标识；
- 右侧洞察卡中的样本量、p 值和证据入口。

## 0:18–0:42 输入与隐私

**操作**：点击“载入示例数据”。

**讲解词**：

“我们使用一份 720 行、10 个字段的合成社区数据，包含六个区的收入、客流、满意度、投诉和商业活力指标。CSV 和 XLSX 都由浏览器前端解析，统计在 Web Worker 中运行，数据不会上传服务器。”

**观察点**：

- 加载态说明解析、画像、检验和排序过程；
- 结果页显示 720 条记录、10 个字段、缺失率与可复核洞察数；
- 顶部有“浏览器 Web Worker”标记。

## 0:42–1:08 自动洞察与证据指标

**操作**：在工作台点击第一条洞察卡片。

**讲解词**：

“系统自动完成了字段画像、缺失审计、异常检测、相关分析、分组检验和时间变点检测。每条洞察不是一段孤立文案，而是同时给出有效样本量、方法、效应量和 p 值。这里看到的排序分，由证据强度和风险共同决定。”

**指向屏幕**：

- 左侧洞察排序列表；
- 主叙事摘要；
- 四项证据指标：n、效应量、显著性、排序分；
- 推荐图表及“为什么用这张图”说明。

## 1:08–1:38 证据抽屉与可追溯性

**操作**：点击“打开完整证据抽屉”。

**讲解词**：

“打开证据抽屉，可以看到从数据到结论的完整链路：使用的是哪个数据集、应用了哪些筛选条件、采用什么统计方法、产生了多少有效样本，以及支撑这条结论的聚合证据表。相关关系会明确标注不等于因果，异常值也不会被自动删除。”

**操作**：展示证据表，然后关闭抽屉。

**讲解词补充**：

“抽屉中的证据链可以复制为 JSON，便于审计和复现。”

## 1:38–2:08 追问式下钻

**操作**：点击当前洞察下方的第一个追问按钮，例如“下钻至最高组”。

**讲解词**：

“数镜支持追问式下钻。点击追问后，系统生成新的结构化筛选条件，在 Worker 中重新执行全部统计，并保留追问链。这样，叙事和计算始终共享同一组条件，而不是只换一张静态图。”

**观察点**：

- 筛选条件 chip；
- 样本量变化；
- 洞察列表重新排序；
- 追问历史记录。

## 2:08–2:32 图表、质量检查与报告

**操作**：

1. 切换“字段画像”，展示自动类型与描述统计；
2. 切换“质量检查”，展示缺失/IQR 异常；
3. 回到洞察工作台，点击“导出报告”。

**讲解词**：

“字段画像帮助评委确认系统是否正确理解数据；质量检查把缺失和异常摆在结论前面。最后，报告导出会把当前筛选条件、方法、效应量、证据表和解释边界固化下来，可生成 Markdown 或打印为 PDF 的 HTML。”

## 2:32–2:50 技术实现

**讲解词**：

“技术栈是 React、TypeScript、Vite、Web Worker、ECharts 和项目内统计实现。CSV 与 XLSX 在浏览器解析，相关检验、Welch、ANOVA、IQR 和变点置换检验均由项目自身完成。GitHub Pages 只托管静态资源，没有后端依赖，也没有必需的 GPU 或外部 AI API。”

## 2:50–3:00 收束

**讲解词**：

“数镜的价值不是替人下结论，而是让结论变得可以检查、可以追问、可以复现。谢谢各位评委老师。”

## 演示前检查清单

- 使用生产构建预览，不用开发热更新遮挡画面；
- 确认 4174 端口未被其他项目占用；
- 示例数据可加载；
- 第一条洞察可打开证据抽屉；
- 浏览器允许下载文件；
- 关闭无关通知和浏览器标签页；
- 预备本地 CSV 作为网络故障时的替代输入。

## 时间不足时的删减顺序

1. 先删字段画像展示，保留质量检查；
2. 将报告导出压缩为一句“支持 Markdown 与 HTML”；
3. 证据抽屉只展示统计口径和证据表，不展开解释边界；
4. 不建议删“追问后样本量变化”，这是作品最核心的差异化交互。
